# Архитектура DualVPN

## Цель

SIM со специальным APN сама по себе не даёт обычный интернет, но позволяет
достичь VPN-сервера. LT300 строит поверх LTE один из двух туннелей и раздаёт LAN
и Wi-Fi уже как клиентов удалённой сети.

```text
телефоны/ноутбуки
        │
     br-lan
        │
 firewall zone lan
        │
 firewall zone vpn + masquerade
        │
  wg0 ИЛИ awg0             выбранный default route
        │
 VPN endpoint /32          всегда напрямую через LTE
        │
 usb0 / wwan               metric 100
        │
 специальный APN
```

## Почему оба `route_allowed_ips=1` использовать нельзя

Если оба peer с `AllowedIPs = 0.0.0.0/0` одновременно создают маршрут по
умолчанию, результат зависит от порядка запуска netifd, метрик и времени
handshake. Возможны два default route, отправка endpoint внутрь самого туннеля и
потеря доступа после reboot.

В этой схеме у обоих peer:

```text
route_allowed_ips=0
nohostroute=1
```

Маршруты создаёт только `/usr/sbin/vpn-apply-route`:

1. получает реальный `l3_device` и gateway интерфейса `wwan`;
2. создаёт `/32` до endpoint обоих VPN через LTE;
3. убеждается, что выбранный tunnel interface поднят;
4. заменяет default route на `dev wg0` или `dev awg0` с metric 10.

WWAN сохраняет резервный default route с metric 100, но firewall не разрешает
обычный LAN → WAN forwarding. Он нужен роутеру для endpoint, времени и
диагностики, а не для обхода kill switch клиентами.

## Безопасное ручное переключение

`vpn-switch` не удаляет рабочий default route заранее. Для целевого туннеля он:

1. запускает `ifup`;
2. временно добавляет только маршрут `/32` к `probe_ip` через целевой interface;
3. ждёт ненулевой handshake;
4. проверяет ping с `-I <target-interface>`;
5. только после успеха вызывает `vpn-apply-route`;
6. сохраняет режим в `/etc/config/vpnmode`.

Если preflight не проходит, действующий режим не меняется. Именно поэтому
команды могут ответить `failed the handshake/traffic test`: это защита, а не
ошибка кнопки.

Команды:

```sh
/usr/sbin/vpn-use-wg
/usr/sbin/vpn-use-awg
/usr/sbin/vpn-status
```

Символические ссылки указывают на один `vpn-switch`, который определяет действие
по имени запуска. LuCI Custom Commands вызывает те же файлы.

## Почему автоматический failover выключен

На мобильном канале кратковременно меняются latency, packet loss и доступность
ICMP. Агрессивный watchdog способен принять временный всплеск за отказ и начать
переключать туннели туда-сюда. Это ухудшает связь и затрудняет диагностику.

В проекте `auto_failover=0`. Автоматизировать переключение имеет смысл только
после длительного сбора статистики и с гистерезисом:

- несколько последовательных провалов;
- минимальное время в текущем режиме;
- отдельный порог возврата;
- проверка handshake и прикладного трафика;
- журнал причины каждого решения.

## Восстановление после reboot

LTE-модем, системное время и VPN handshake появляются не одновременно.
`vpn-restore-mode` ждёт 15 секунд и затем ограниченное число раз пытается вызвать
команду сохранённого режима. После первого успеха процесс завершается. Это
one-shot boot recovery, а не постоянный watchdog.

Hotplug `96-vpn-route` повторно создаёт endpoint routes после `ifup` WWAN.

## Время без RTC

У LT300 нет часов реального времени. После cold boot дата может быть неверной,
что мешает DNS/TLS и диагностике. `95-vpn-clock` после `ifup` WWAN запускает
`awg-sync-modem-time`, который читает `AT+CCLK?` с `/dev/ttyUSB2` и задаёт UTC.

На проверенном модеме `AT+CCLK?` возвращал UTC. На другом модеме проверьте формат
и timezone suffix до использования скрипта. После появления нормального
интернета время уточняет NTP.

## Firewall и kill switch

Создаётся единая zone `vpn`:

```text
network: wg0, awg0
input:   REJECT
output:  ACCEPT
forward: REJECT
masq:    1
mtu_fix: 1
```

Разрешено `lan → vpn`. Существующие `lan → wan` forwarding отключаются. Поэтому
падение туннеля не превращается в незаметный прямой выход через SIM.

Проверка:

```sh
uci show firewall.vpn
uci show firewall.lan_to_vpn
uci show firewall | grep '=forwarding'
fw4 check
```

## Клиент за роутером со своим VPN

Без исключения пакет такого клиента к тому же серверному endpoint попадает в
default VPN роутера и создаёт рекурсию. Установщик добавляет отдельные firewall
rules LAN → WAN для UDP endpoint/port WG и AWG. Поскольку сам роутер держит
endpoint `/32` через LTE, downstream-клиент подключается напрямую через APN.

Автоматическое правило создаётся только для literal IPv4. Если в конфиге указан
hostname, закрепите его адрес самостоятельно и учтите возможную смену DNS.

Проверка:

```sh
ip -4 route get <VPN_ENDPOINT_IP>
uci show firewall.vpn_endpoint_wg
uci show firewall.vpn_endpoint_awg
```

## Удалённое управление роутером через VPN

Firewall-зона `vpn` имеет `input=REJECT`, поэтому поднятый туннель сам по себе не
открывает управление. Установщик добавляет только TCP/22 для источников:

- WireGuard: `10.8.1.0/24`;
- AmneziaWG: `10.8.2.0/23`.

Одновременно создаются маршруты к этим сетям через `wg0` и `awg0`. Они обеспечивают
симметричный ответ: если default сейчас через AWG, ответ клиенту, пришедшему по WG,
всё равно уходит обратно в WG. LTE/WAN правила не затрагивают.

VPN-сервер также обязан маршрутизировать клиентские сети к peer роутера, а peer
администратора — иметь маршрут к VPN-адресу роутера. Для входа используется
`ssh root@<Address_интерфейса_роутера>`, не LAN-адрес `192.168.x.1`.

## DNS

Импортёр берёт `DNS=` из клиентского конфига и задаёт dnsmasq:

```text
noresolv=1
server=<VPN_DNS_1>
server=<VPN_DNS_2>
```

Если внутренний DNS доступен только через один туннель, переключение на другой
даст ложное впечатление «VPN подключён, но интернета нет». Для dual-mode
используйте DNS, доступный через оба туннеля, либо несколько серверов.

## WireGuard против AmneziaWG 2.0

Обычный WireGuard обычно быстрее и легче для MT7628AN: меньше обработки пакетов
и нет обфускационных параметров. AmneziaWG полезен там, где обычный WG теряет
пакеты или фильтруется. Фактическая скорость ограничена CPU 580 МГц, LTE,
сервером, MTU и Wi-Fi — сравнивайте на одном сервере и одинаковом маршруте.

## IPv6

Peer-примеры содержат `::/0`, но финальная IPv6-схема зависит от того, выдаёт ли
сервер IPv6 и настроен ли forwarding. Если IPv6 не проверен, безопаснее не
анонсировать клиентам IPv6 default route, чем допустить обход IPv4 kill switch.
